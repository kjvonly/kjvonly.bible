# KJVOnly Architecture Principles

This document describes the architectural principles that guide every Architecture Decision Record (ADR) in this repository.

These principles are intentionally few in number.

Whenever new functionality is added to the application, these principles should be considered before introducing new architectural concepts.

The goal is not simply to reduce code duplication.

The goal is to build a system with a small, consistent set of architectural concepts that compose naturally over time.

---

# Everything Is a Resource

Resources are the fundamental unit of the architecture.

Bible data, overlays, notes, reading plans, search indexes, manifests, publisher metadata, and export archives are all resources.

The application requests resources by identity rather than by storage location.

---

# Resources Have Stable Identity

Resources have one canonical identity.

Their identity does not change because they are moved, downloaded, exported, published, or stored using a different transport.

Versions change.

Identity does not.

---

# Everything Begins with a Manifest

Resources are discovered through manifests.

A manifest describes what resources exist, where they can be resolved, and how they should be installed.

Regardless of where a manifest comes from, the application processes it the same way.

---

# One Installation Pipeline

The application has a single installation pipeline.

```text
Source

↓

Manifest

↓

Verify

↓

Resolve Resources

↓

Install

↓

Domain Stores
```

The source may be:

* Trusted Publisher
* Export Archive
* Local File
* HTTP
* Future discovery mechanisms

Only the source changes.

The installation process remains the same.

---

# Compose Existing Concepts

Before introducing a new architectural concept, determine whether the capability can be expressed by composing concepts that already exist.

Prefer:

```text
Manifest

+

Resources

=

Archive
```

over inventing a separate backup architecture.

Prefer:

```text
Discovery

+

Subscriptions

=

Publisher Installation
```

over combining trust and installation into a single concept.

Architectural concepts should be reused before new ones are created.

This is DRY applied to architecture rather than implementation.

---

# Separation of Concerns

Each architectural layer has a single responsibility.

```text
Kinds

↓

Resources

↓

Discovery

↓

Resolution

↓

Installation

↓

Domain Stores

↓

Synchronization
```

Layers communicate through well-defined interfaces.

A layer should not assume how another layer performs its work.

---

# Offline First

The application always prefers local operation.

Network connectivity enhances the application but should not be required for normal use.

All user interactions complete locally.

Synchronization occurs independently.

---

# Trust Enables Discovery

Trust determines which publishers the application may discover resources from.

Trust does not install resources.

---

# Subscription Enables Installation

Discovery and installation are separate decisions.

Users may trust a publisher without installing every resource that publisher provides.

Subscriptions determine which discovered resources become part of the local application.

---

# Publisher Ownership

Resources always belong to their publisher.

Ownership does not change when a resource is downloaded, imported, or installed.

Users create new resources by publishing their own copies rather than modifying another publisher's work.

---

# Derived Data Is Still a Resource

Data generated by the application may still be treated as a resource.

Examples include search indexes and export archives.

If derived data provides long-term value, it should participate in the same resource-oriented architecture as primary data.

---

# Storage Independence

Storage is an implementation detail.

Resources may be resolved from Blossom today and another storage provider tomorrow without changing resource identity or application behavior.

The architecture depends on resources, not storage technologies.

---

# Keep the Architecture Small

New functionality should increase capability without increasing conceptual complexity.

When faced with multiple solutions, prefer the one that reuses existing architectural concepts.

A small set of consistent ideas is easier to understand, easier to maintain, and more likely to remain coherent as the system evolves.
